# 物品数据提取原理与独立实现指南

本说明给出从客户端文件独立实现物品提取所需的数据布局、算法、关联规则和验收方法。实现语言与工具可以替换。下列具体常量和字段位置已在客户端 **0.95.2、data revision 1379138、resource revision 1359983** 上验证；版本变化后必须重新确认，不代表官方 schema。

目标是取得主物品 ID、中英文名称、类别、标签、说明、图标及来源证据。保留所有主物品记录，包括占位、场景、测试和任务内容；不能将配置存在等同于已开放或可获得。获取途径、价格、种植关系和其他属性尚未完成字段确认，不凭猜测输出。

## 1. 输入与版本一致性

客户端是 Unity/IL2CPP 实现，主要输入如下。路径以客户端根目录或其 `PetitPlanet_Data` 目录为基准：

本仓库的客户端根目录按版本组织为 `resources/petit-planet-game/<版本>/`；同版本的对象索引位于 `resources/petit-planet-extraction/<版本>/index/`，供各提取任务共用，物品产物写入同版本 items 目录。目录版本号与热更新 revision 不混用。索引移动不改变内容，读取时需重定位其旧 Source 路径。

| 输入                                                                  | 用途                                       |
| --------------------------------------------------------------------- | ------------------------------------------ |
| config.ini 的 game_version                                            | 客户端版本标记，不等于热更新 revision      |
| StreamingAssets/GenerateAssets/ed.obb                                 | 基础集中配置                               |
| StreamingAssets/GenerateAssets/cs.obb                                 | 基础文件/目录索引                          |
| StreamingAssets/res_revision.json、res_versions.json                  | 基础资源版本与文件校验清单                 |
| Persistent/versions/<清单目录>/data_revision.json、data_versions.json | 更新配置版本与文件清单                     |
| 同目录的 res_revision.json、res_versions.json                         | 更新资源版本与文件清单                     |
| Persistent/GenerateAssets、Persistent/Temp/<清单目录>/GenerateAssets  | 更新配置候选位置，不能漏掉 Temp            |
| StreamingAssets/AssetBundle、Persistent/AssetBundle                   | 基础和更新 Unity 资源包                    |
| Unity 对象索引（Asset Map）                                           | 名称、类型、Container、PathID 与资源包位置 |

这些名为 `*_versions.json` 的文件实际是 CSV：首行为 `FilePath,md5,FileSize`。解析内容而不是按扩展名认定 JSON。先选择一个明确的本地版本清单，再按条目核对文件大小及 MD5。只采用两份 OBB 都匹配同一个 data 清单的完整配置对，并保存路径、revision、MD5、SHA256。当前匹配位置是 `Persistent/Temp/5662883/GenerateAssets`；只检查基础目录会误用旧配置。

资源与配置拥有各自的 revision。资源对象同时存在于基础和更新索引时，保留所有来源，优先考虑更新版本；实际导出的每个来源包必须匹配对应清单。基础包按基础 res 清单核对，更新包优先查 data 清单中的同路径条目，再查更新 res 清单。优先级不是“哪个文件更新时间较新”。本地清单不能证明线上版本最新。

Asset Map 可通过支持该客户端的 Unity 资源工具生成；需要覆盖基础和 Persistent 更新资源。当前验证工具为 AnimeStudio，游戏模式 HYG_CB1。索引必须至少保留以下字段：

| 字段      | 要求                                                 |
| --------- | ---------------------------------------------------- |
| Type      | 区分 Texture2D、Sprite 等 Unity 对象                 |
| Name      | 实际对象名；图集中尤其重要                           |
| Container | 原资源路径，不是本地导出文件名                       |
| PathID    | 64 位有符号对象 ID，作为字符串保存，避免 JS 精度丢失 |
| Source    | 包文件位置；移动客户端时按客户端内部相对路径重新定位 |

当前 XML 是逐行的 `<Asset>` 记录；读取时须解码 XML 实体，不因关键词过滤漏掉合法 Sprite。只在名称中搜索 item/fish 等关键词不足以覆盖所有图标。

## 2. 数字与字节数组解码

OBB 不是 ZIP 或明文 JSON。结构类似 FlatBuffers，但数字和字节数组有自定义变换。下面所有位置都是**文件字节偏移**，字段序号从 0 开始。

固定宽度数字：

```text
u32(p) = unsigned32(read_uint32_big_endian(p) XOR 0x53020253)
i32(p) = reinterpret_as_signed32(u32(p))
u16(p) = read_uint16_big_endian(p) XOR 0x5555
ref(p) = p + u32(p)
```

字节数组通用解码，其中 n 是数组的字节长度，不是字符数：

```text
key = unsigned32(n XOR 0x01350257)
mask = [key & 255, (key >> 8) & 255, (key >> 16) & 255, (key >> 24) & 255]
allocate out[n]
for i in 0 .. n-1:
    j = n-1-i
    mask_index = 0 if i == j else min(i, j) modulo 4
    out[j] = input[i] XOR mask[mask_index]
```

数组被反转，掩码按离端点的距离镜像循环；奇数中心始终使用 mask[0]。长度超过 255 时，必须计算长度的高字节。不能只做固定 XOR，也不能把每个字符当成一个字节。

其他宽度的标量可对其完整字节宽度使用上述变换，再按小端读取无符号值。例如 64 位哈希桶先解码 8 字节，再读 uint64 little-endian，必须使用 BigInt 或等价的精确整数类型。

## 3. 对象、引用与向量布局

读取文件首 4 字节，`root = u32(0)`；当前 ed.obb 的 root 为 1512。对象 t 的字段地址由 vtable 确定：

```text
vtable = t - i32(t)              # 必须使用有符号值；vtable 可能在对象后方
vtable_length = u16(vtable)      # 字节数，含前 4 字节
object_size = u16(vtable + 2)
field_count = (vtable_length - 4) / 2
offset(k) = u16(vtable + 4 + 2*k)
field_address(k) = null if offset(k) == 0 else t + offset(k)
```

先校验偏移、长度、偶数 vtable 长度、完整对象范围以及 `0 < offset < object_size`，再解引用。字段不在 vtable 中或 offset 为 0 表示缺失，不应读文件位置 0。vtable 可以共享，不能根据地址先后关系认定损坏。

普通行集合：根字段地址 → `ref` 到包装对象 → 包装字段 0 的地址 → `ref` 到向量 v。`u32(v)` 是行数，行 i 的对象地址为 `ref(v + 4 + i*4)`。校验整个偏移数组，再按上述对象算法读取每行。当前根字段 1 是 TextMap 字典，必须排除在普通行向量扫描之外。

字符串字段地址 p：`s = ref(p)`，`n = u32(s)`，取 `s+4` 开始的 n 个字节，按第 2 节解码，再严格 UTF-8 解码。检查完整范围、合理长度及非法控制字符。不要把尾部零字节算进字符串。字符串的“可解码”只说明它是候选，不能据此确认字段的业务含义；数值或引用可能碰巧被误识别。

## 4. TextMap 字典

根字段 1 解引用得到包装对象 W，W 的字段 0 再解引用得到字典对象 D。当前 D 使用以下字段：

| 字段 | 含义             |
| ---- | ---------------- |
| 0    | 元素数量（u32）  |
| 3    | 哈希桶向量引用   |
| 4    | 文本记录引用向量 |

两个向量的首 u32 分别是桶数和记录数。哈希桶每项 **8 字节**，文本记录引用每项 **4 字节**。桶解码：

```text
value = decode_8_bytes_then_uint64_little_endian(bucket_address)
low = value AND 0xffffffff
hash = value >> 32
if low == 0xffffffff: skip empty bucket
index = low >> 8                 # 低 8 位不是行索引的一部分
text_record = ref(values_vector + 4 + index*4)
```

检查 `index < value_count`、每个 hash 唯一，以及有效桶数 = D.field0 = value_count。当前有效记录 116,673，桶数 233,343。文本记录本身不含 hash 字段，不能在其字符串里寻找 key。

每条文本记录是含 15 个字符串字段的对象：0 英文、1 简体中文、2 繁体中文、3 法文、4 德文、5 西班牙文、6 葡萄牙文、7 俄文、8 日文、9 韩文、10 泰文、11 越南文、12 印尼文、13 土耳其文、14 意大利文。本次基础库使用简中和英文，输出 `hash → {zh,en}`。缺失英文可以为空，当前所有简中都存在。

## 5. 业务集合与关联

以下标签来自内容和跨表证据，不是已还原的官方表名。读取这些字段时使用明确的位置，不把通用探针的所有猜测导入数据库。

| 根字段 | 集合作用           | 行内字段                                                                                         |
| ------ | ------------------ | ------------------------------------------------------------------------------------------------ |
| 318    | 主物品，6,002 行   | 0 ID；1 名称 TextMap hash；2 主类别 ID；3 待确认第二类型代码；6 分类标签字符串；7 检索标签字符串 |
| 325    | 显示配置，4,753 行 | 0 ID；4 小图标字符串；5 大图标字符串；27 说明 TextMap hash                                       |
| 716    | 类别，101 行       | 0 类别 ID；1 类别名字符串                                                                        |
| 186    | 生物图鉴，322 行   | 0 ID；1 名称 TextMap hash；6 直接存储的长说明；11 图鉴图标字符串                                 |

以 318 为主集合：名称由 field1 关联 TextMap；类别由 field2 关联 716.field0；显示配置按 ID 左连接 325，再解析小/大图标和说明。所有主物品必须保留，不能只取有图标或显示行的交集。检查主 ID 唯一；未能解析名称或主类别时停止验收，不用文件名生成替代名称。

3 号字段暂不作为父类别或类别继承；标签保留原字符串，不擅自按标点拆成数组。图鉴名称与主表名称的 hash 可以不同；同 ID 的名称差异需要分别记录，主名称保留主表文本，不自动纠正用字或删除“占位”。目前 319 个共同生物 ID 中 310 个同名，9 个不同。

已找到其他扩展集合：262 家具、519 服装、232/137 作物相关。其详细字段尚未纳入已确认的基础提取；不要根据 ID 相似度直接合并种子、苗和产物。

cs.obb 是文件/目录索引，并非业务 schema：首指针到根对象，根字段 0 引用内部对象；内部字段 0/1 是文件名/目录名字符串引用向量，2/3 是目录相关数字数组，4/6 是文件相关记录引用向量，5 是目录相关记录引用向量。可取得 ExcelData、TextMap 名称作为重新定位线索，但这些哈希尚未被证实能直接映射全部根字段或 MiHoYoBinData 文件名。

## 6. 图标匹配、图集与导出

对显示配置的 `UISprite/...` 引用加前缀 `assets/moleres/rel/sres/`，将分隔符变为 `/`、转小写，并仅去除末尾 png/jpg/jpeg/tga/psd 扩展名；对 Container 做相同处理，按完整路径精确连接 Texture2D。保留基础与更新来源变体，按第 1 节选择来源。

不要使用图标文件名数字前缀作为物品 ID 关联。例如主物品 ID 16 是“绵朵莉手作玩偶铺”，真实引用 `UISprite/Load/BigPic/DIYHandbook_TopicFurn/TopicFurn_016.png`；旧 `16_...` 图片可能属于其他物品。

Texture2D 名称以 `sactx-` 开头时通常是图集。必须同时用**完整 Container 和精确 Sprite 名称**匹配：名称为配置引用的最后一段去扩展名。若未找到对应 Sprite，不得把整张图集当成物品图片。同名 Sprite 也可能存在于 `assets/art/...` 与目标路径，导出时同时过滤名称和 Container。

每条记录优先选能匹配的小图，否则选能匹配的大图。按 Source+PathID 去重，按来源包和 Unity 对象类型分组，用支持当前格式的工具导出：普通对象导出 Texture2D PNG，图集子图导出 Sprite PNG。HYG_CB1 是当前已验证模式；使用精确筛选，避免一次加载整个客户端。工具退出失败或选定对象未生成有效 PNG 必须记录并使流程失败。

图标文件可以按标准化 Container 的稳定哈希命名，映射中保留配置引用、Container、Source、PathID、对象类型、文件路径、尺寸和 SHA256。多条物品可能共用一图，因此图标数不是物品数。

## 7. 输出与验收

至少输出主物品集合、类别集合、图标文件和映射、来源版本及缺失清单。每条主记录包括：ID、中英文名、名称 hash、主类别 ID/名称、待确认第二类型代码、标签、说明、小/大图引用、选定本地图片、图标状态、配置文件与根字段/行偏移。图片路径相对数据集目录；`availability` 保持 `unknown`。

图标状态区分：已有 PNG、引用存在但索引未匹配、没有已识别引用、选定对象导出失败。零引用不是工具错误；不要用猜测图片掩盖缺失。JSON 保留来源对象；CSV 使用 UTF-8 BOM、正确引用逗号/引号/换行；SQLite 按主类别和图标键建立关联，运行完整性和外键检查。

## 8. 客户端变化后的调查顺序

1. 固定版本清单与文件校验值；重新发现有效配置对，不沿用旧偏移或缓存。
2. 用根对象、字段范围及短/奇数/长字符串核对数值与字节算法；失败则先恢复编码。
3. 遍历候选根集合，利用已知物品样例、ID 唯一性、名称哈希覆盖和类别关联定位主表。
4. 单独恢复 TextMap 字典，确认语言与桶布局；验证名称覆盖，而非只看几个可读字符串。
5. 重新定位显示表，核对图标真实路径和不同类别样例；处理基础/更新与 Sprite 变体。
6. 将字段逐项标为已确认或候选，完整生成并验收后才用于数据库。统计变化本身不证明算法错误，也不证明新增记录已经开放。

本说明对未知字段不做断言。新版本需要修改已验证常量、字段位置或指标时，保存重新确认的依据，而不是放宽检查来使旧实现通过。
